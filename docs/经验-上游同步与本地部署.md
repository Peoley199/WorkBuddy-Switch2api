# 上游同步与本地部署 · 经验手册

> 来源：2026-10-24（首次手工同步）与 2026-10-30（第二次，同步 e9bacf0 → 2f65a05）两次实做的复盘。
> 适用范围：本仓库（cv-superding 的 fork）从上游同步代码、合并、推远端、构建部署的完整流程。
> 配套脚本：`scripts/upstream-sync.sh`、`scripts/deploy-local.sh`。
> 硬性规则与逐次记录在 [UPSTREAM-SYNC.md](UPSTREAM-SYNC.md)，本文讲**怎么把事做成**。

## 0. 一页速查

```bash
# ① 同步
sh scripts/upstream-sync.sh              # 调查 + 导出差异 + 风险扫描 + 备份 + 开分支
#   然后人工逐条决策、移植、写账本
sh scripts/upstream-sync.sh --verify     # 测试 / clippy 增量 / 账本与 Upstream 说明检查
git checkout main && git merge --no-ff sync/upstream-<sha>
git merge -s ours upstream/main -m "merge(-s ours)：标记上游 <sha> 已同步"
git push origin main

# ② 部署
sh scripts/deploy-local.sh               # 预检 → 构建 → 备份 → 替换 → 重启 → 探活（失败自动回滚）
sh scripts/deploy-local.sh --dry-run     # 只看预检与构建，不动运行中的程序
```

## 1. 为什么不能直接 merge

| 直接 merge 的后果 | 实测证据 |
|---|---|
| 冲突块成片，且合并后**两套逻辑并存** | 2026-10-24 在 `proxy.rs` 产生 8 个冲突块 |
| 覆盖本仓库独有功能（上游不知道这些功能存在） | Anthropic 兼容层、http_guard、11140 三分流、出站头族 |
| 版本号被上游覆盖 → 旧客户端更新链断 | `tauri.conf.json` 的 updater pubkey 两仓库不同 |
| GitHub 的「落后 N 个提交」提示不会消失 | 需要 `-s ours` 记账合并才能归零 |

**根本原因**：两边不是简单的「上游领先」关系，而是**各自独立演进**。上游修 11140 用了三版迭代
（v1.6.25 固定 6h → v1.6.26 改 3h → v1.6.27 递增冷却），本仓库早在 10-28 就做了按 displayMsg
三分流的 `ban_kind()`——两套方案在同一函数上互斥，只能人工择一。

## 2. 调查阶段：先建立事实，再谈方案

### 2.1 必查的四件事

```bash
git fetch upstream
git log upstream/main --not main --oneline --date=short --pretty=format:"%h %ad %s"  # 有哪些新提交
git log upstream/main --not main --reverse --stat                                     # 各自改了什么文件
git diff <上次同步点>..upstream/main -- crates/wb-switch-core/src/modules/proxy.rs     # 累计差异
git status --short                                                                     # 本地有没有未提交改动
```

⚠️ **最容易翻车的一点**：本地若有未提交改动，必须**先落库再同步**。否则同步 diff 会和它搅在一起，
事后无法分清「哪些是我改的、哪些是上游的」。

### 2.2 判断「是否已同步」只能看 sha，不能看版本号

两仓库的版本号各自独立。2026-10-30 那次两边都停在 `1.6.27` 但内容完全不同。
唯一可靠判据：

```bash
git log upstream/main --not main --oneline   # 空 = 已同步
```

### 2.3 自动化能做什么、不能做什么

`upstream-sync.sh` 自动做完这些：

- 拉取（含**断网降级**：15s 硬超时，失败则用本地已有引用并显式警告「结论可能不是最新」）
- 逐提交导出 diff 到 `/tmp/wb-upstream/<sha>.diff`（代码与文档/清单分块，便于分别看）
- **自动风险扫描**（见下节）
- 生成决策表 `SUMMARY.md`（每行留空待填）
- 备份分支 + 仓库外 bundle
- 开 `sync/upstream-<sha>` 分支并跑基线测试

它**不做**决策与移植——这必须人工。上游不知道本仓库有什么，整块取一侧会静默删掉保护项。

### 2.4 风险扫描覆盖的三类（都是踩过的坑）

| 扫描项 | 为什么值得扫 |
|---|---|
| 上游删除了 `#[test]` 属性 | **真实发生过**：`4ea798a` 删了 3 个（含 `tool_choice` 归一化与按版本取号）。编译通过、测试静默不运行，不看 diff 根本发现不了 |
| 保护清单文件被改动 | `package.json`（签名脚本）、`tauri.conf.json`（updater pubkey）、两个 lock |
| 独有功能锚点被触碰 | `chat_headers` / `is_channel_block` / `has_upstream_code` / `ban_kind` / `11140` / `http_guard` / `anthropic` |

## 3. 决策阶段：每个提交怎么判

### 3.1 四种结论

| 结论 | 适用 | 动手方式 |
|---|---|---|
| **原样移植** | 纯新增功能，本地无对应实现 | `git cherry-pick <sha>`，然后 `--amend` 补 `Upstream:` 行 |
| **移植 + 修正** | 功能要，但判定函数/文案与本地实现冲突 | 手工编辑，逐函数对齐 |
| **文档采纳，代码跳过** | 上游修的问题本地早已修好，但复盘文档有价值 | 只改 `.md` |
| **不同步** | 版本号、与本地方案互斥的实现 | 在账本写清理由 |

### 3.2 判断「谁更好」而不是「谁是上游」

2026-10-30 的 11140 是最典型的例子：

| 维度 | 上游 v1.6.25–27 | 本仓库 |
|---|---|---|
| 语义分类 | 无——任何 11140 都当账号风控 | `ban_kind()` 三分流（账号级/内容审核/未知） |
| 分类依据 | 2026-10-29 单次实测 | 两个独立社区实测（2026-09-17 起），确认 11140 是**双语义码** |
| 账号级处置 | 递增冷却 3h→6h→12h→24h（不持久） | 写 `needs_relogin` **持久摘号** |
| 内容审核 | 会被误判成封号 | 完全不碰账号 |

结论：保留本地方案，但**采纳上游的 Trace ID 提取**（那是它 10-29 实测换来的增量信息）。
**取向不是「谁新听谁的」，而是「哪套假设经得起验证」。**

上游方案里被自身实测证伪的假设值得记住：它先按社区口径定「2~4 小时自解」，后来实测
**等 2 天未恢复**，才改成递增冷却——这个纠错过程本身就说明「社区口径 ≠ 本案事实」。

### 3.3 移植时的三个具体陷阱

1. **`is_channel_block` 的 `request illegal` 裸兜底不能要**。11140 的 `msg` 与 11128 一字不差；
   上游靠先查 11140 挡住，但它的 2 形态匹配遇转义体（`code\":11140`）会漏判，导致被封号进渠道重试循环。
   本仓库 8 形态匹配 + `ban_kind` 前置分流已覆盖。
2. **函数签名差异**：上游测试用 `next_uid_of(Some(ed), None)`（2 参），本仓库是 3 参
   （多一个 `exclude: &[String]`）。移植测试必须改签名。
3. **提交说明必须带 `Upstream: <repo>@<sha>`**，否则 `--verify` 会挑出来，且账本无法追溯。

## 4. 收尾：验证 → 合并 → 让远端「落后数」归零

### 4.1 `--verify` 查什么

| 检查 | 判据 |
|---|---|
| 工作区 | 只拦**已跟踪**文件（未跟踪的调研资料不阻断） |
| 账本 | `docs/UPSTREAM-SYNC.md` 自备份分支以来必须有改动 |
| 提交说明 | 每个提交要有 `Upstream:` 行（文档/杂项可忽略） |
| 测试 | `cargo test -p wb-switch-core` 全绿 |
| clippy | **增量对比**：在基线 worktree 上跑一次、HEAD 跑一次，忽略行号后逐条 diff，**不允许新增** |

clippy 必须比增量而不是看绝对数：本仓库有 45 条历史警告，修正它们属于另一件事，
不该混进同步提交。

### 4.2 两步合并

```bash
git checkout main
git merge --no-ff sync/upstream-<sha>          # ① 内容合并（保留同步分支的结构）
git merge -s ours upstream/main -m "..."       # ② 记账：标记上游已同步
git push origin main
```

第②步是**只动历史、不动文件**的合并。它的唯一作用：让 `git log upstream/main --not main` 归零。

**为什么需要它——这直接关系到 GitHub 上的提示**：
GitHub 的「This branch is N commits behind」就是按「上游有多少提交不是本分支的祖先」算的。
不做 `-s ours`，哪怕内容早就手工移植完了，上游那 8 个提交也不是我们的祖先，
GitHub 会一直提示落后、按钮一直亮着。做完之后实测：

```
GET /repos/cv-superding/WorkBuddy-Switch2api/compare/main...Peoley199:main
→ "status": "ahead", "ahead_by": 26, "behind_by": 0
```

`behind_by: 0` = 提示消失；`ahead_by: 26` = 我们自己的独立演进，正常状态。

### 4.3 版本号：用工具，别用 sed

2026-10-30 实测教训：手写 `sed 's/1.6.27/1.6.28/'` 补版本号，**漏了 `npm/package.json` 里
`optionalDependencies` 的 4 个平台包版本**。是部署脚本的 `version.mjs check` 预检拦下的。

```bash
node scripts/version.mjs check      # 17 个位置是否一致
node scripts/version.mjs set 1.6.28 # 一次性全改 + 刷新 Cargo.lock
```

## 5. 构建与部署

### 5.1 手工步骤（脚本已自动化）

```bash
node scripts/version.mjs check        # 全部一致？
npm run build                         # 前端源码有改动才需要
cargo build --release -p wb-switch-rust
# 停进程 → 备份 → 覆盖 → 重启 → 探活
```

### 5.2 `deploy-local.sh` 的四道防线（都是实测踩出来的）

**防线 1：产物冒烟测试（部署前）**

坏件绝不能进部署目录。判据：文件头是 `MZ` + 能被系统加载（坏 PE 会 `Exec format error`）。

> 为什么这条最重要：一旦坏件装进部署目录，**下一次部署的「备份旧版」备份的就是它**，
> 回滚只能回到坏件——备份链被永久污染。2026-10-30 实测踩过：连续几次测试后，
> 部署目录躺着截断件，回滚"成功"却仍然起不来。

**防线 2：启动失败也走回滚路径**

早期版本用 `die "启动失败"` 直接退出，结果坏 exe 留在目录、服务停摆，比不部署更糟。

**防线 3：回滚后必须验证**

备份本身可能就是坏的。回滚完要确认进程起来了、端口通了；否则**明确报警并列出可用历史备份**，
而不是打印「已回滚」给人虚假安全感。实测输出：

```
✗ 回滚后服务仍未起来 —— 备份件本身可能就是坏的
    请手工选择一份可用的历史备份覆盖 ...
      线索：5000000 字节这种明显偏小的文件是截断件，别用。
```

**防线 4：探活按「不比部署前更差」判定**

不能要求「所有入口必须 200」：国际版长期因账号库无可用号而本来就起不来
（`国际版 入口启动失败: 没有可用的国际版账号`），那不是本次部署的锅。
所以先记录基线，只把「部署前 200 → 部署后不通」算回归。

同时保留一条硬闸：进程起来了却**任何**启用入口都不通 → 视为起坏了，照样回滚。

### 5.3 Windows 特有的两个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `cp` 后立刻算 MD5 对不上 | 刚结束的进程 / 杀软短暂持有文件映射 | 校验加 1s×5 重试 |
| `md5sum \| cut -d' ' -f1` 带出 `\r` | Windows 换行 + `*` 前缀 | 用 `grep -oE '^[0-9a-f]{32}'` 提取 |

### 5.4 部署后如何确认「真的生效了」

不要只看进程在不在。至少做一次真实请求：

```bash
curl -s -H "Authorization: Bearer <proxy.json 里的 key>" \
     http://127.0.0.1:16868/v1/models -o /dev/null -w "%{http_code}\n"
```

脚本已自动对 `proxy.json` 里每个**已启用**入口做这个探活。

## 6. 环境相关的既有事实（别误判成回归）

- **国际版入口 16866 起不来是已知状态**：`accounts.json` 里没有可用的国际版账号时，
  `apply_config` 会报 `没有可用的国际版账号` 并跳过。这与程序版本无关。
- **国内版 16868 是 cch（Docker:23000）依赖的链路**，部署后务必确认它是 200。
- 反代**走直连、不读系统代理**，线路抖动会落到 502（v1.6.23 起文案已改成可读说明）。
- 启动日志重定向在部署目录的 `stderr.log`，排查启动失败优先看它。

## 8. 2026-11-01 第二次实跑的补充（v1.6.28 / v1.6.29）

按本文档完整走了一遍，脚本暴露了 4 个真缺口，全部已修。这些是**照着文档做也会踩到**的。

### 8.1 上游 fetch 的两个坑

**坑一：直连 GitHub 不通，gh-proxy 通。**

```bash
timeout 20 git ls-remote https://github.com/cv-superding/WorkBuddy-Switch2api.git  # 超时
timeout 40 git ls-remote https://hk.gh-proxy.org/https://github.com/...            # OK
```

`origin` 早就配了 gh-proxy，但 `upstream` 当时配的是直连。**两者要一致**：

```bash
git remote set-url upstream https://hk.gh-proxy.org/https://github.com/cv-superding/WorkBuddy-Switch2api.git
```

**坑二：`git fetch --tags` 必然返回非零。**

两仓库版本号各自独立（正是账本反复强调的那件事），所以 **tag 名必然撞车**：

| tag | 本地指向 | 上游指向 |
|---|---|---|
| `v1.6.27` | `94adf40`（我们的提交） | `170cac2` |
| `v1.6.20` | `2773f96` | `8c02926` |

`--tags` 遇到「本地已有同名 tag 但指向不同提交」会返回非零，脚本据此判定「拉取失败」并提示
「结论可能不是最新」——**即使分支引用已经更新成功**。这种假警报很危险：它会让人以为上游没变。

修法：同步只需要分支，**用 `git fetch --no-tags upstream`**。
（不要写成 `git fetch upstream main` —— 那只会更新 `FETCH_HEAD`，`upstream/main`
这个 remote-tracking ref 不动，脚本后面读到的还是旧值。）

### 8.2 `set -euo pipefail` 会静默杀掉部署脚本

这是本轮最危险的一个：**脚本在停掉服务之后静默退出，服务一直没起来，而人以为部署完了**。

```bash
B=$(md5sum "$TARGET" 2>/dev/null | grep -oE '^[0-9a-f]{32}')   # 文件被占用 → grep 返回 1
[ -n "$B" ] && [ "$A" = "$B" ] && break                        # 条件为假 → 返回 1 → set -e 退出
```

两类写法都要避开：

| 反模式 | 后果 | 正确写法 |
|---|---|---|
| `X=$(cmd \| grep ...)`，cmd 可能失败 | pipefail 让赋值失败 → 脚本退出 | `X=$(... \|\| true)` |
| `[ cond ] && [ cond ] && break` | 条件为假即返回非零 → 脚本退出 | `if [ ]; then break; fi` |

**兜底比修 bug 更重要**：部署脚本在「停进程」之后装了一个 `trap ... EXIT`，
任何意外退出都会检查有没有实例在跑，没有就拉起来。宁可退回旧版本继续服务，
也不要停在「服务停摆且没人知道」的状态。

### 8.3 杀软会锁住刚写完的 exe

23 MB 的 exe 刚覆盖完，`md5sum` 会连续几秒读不到（Defender 扫描）。
5 秒重试窗口不够，**拉到 15 秒**才稳。判据是「读不到就重试」而不是「读不到就失败」。

### 8.4 上游 tag 与远端「落后数」互不影响

`behind_by: 0` 只看提交，与 tag 无关。tag 撞车不影响同步结论，只是 `--tags` 的噪音。
如果哪天要发自己的 Release，记得 tag 名会和上游同名 —— 这是既有事实，不是故障。

### 8.5 本轮的判定要点（可作为下次的模板）

| 上游 | 结论 | 判断依据 |
|---|---|---|
| `9aac4e1` v1.6.28 文本指纹清洗 | 移植 + 扩展 | 本仓库只洗 system 且替换词是 `Assistant`（病句）；上游扩到 assistant/developer/工具描述并改用 `DeepSeek`，是纯增量 |
| `ee281bf` 并发上限 / 换号重试 | 移植 | 本地没有，且与风控「账号共享」形状直接相关 |
| `ee281bf` `Pool.sticky` | 跳过 | 本地 `SessionStick` 已接入界面冷却快照，功能更强 |
| `ee281bf` 429 账号级递增退避 | 跳过 | 本仓库对 429 只冻**模型**（6004 口径），冻整账号会停掉还能用的模型 |
| `ee281bf` 5xx 三连熔断 | 跳过 | 国内版只有 1 个号，3 次 5xx = 整池停摆 30 分钟；2026-10-11 的教训正是这个 |

**模式**：同一个提交里，**能独立拿走的功能照拿，与本地既有设计冲突的果断跳**，
并当场把「为什么不取」写进账本 —— 否则下次同步会重新纠结一遍。
