# 国际版账号被封 —— 取证与归因调研报告

> 日期：2026-10-27　｜　方法：4 个子代理并行调查（出站指纹 / 行为指纹 / 外部情报 / 检测面分析）
> ＋ 本机只读取证（上游 403 原始错误体、官方客户端请求头源码、账号与用量时间线）
> ｜　**未修改任何反代代码、未向上游发送任何调试请求**

## 0. 结论先行

1. **这是账号级风控封禁**，不是 token 失效、不是额度耗尽、也不是 TLS 指纹拒绝。
2. 上游返回 **HTTP 403 / bizCode `11140`**，原始文案：
   - `displayMsg.en`: *"Your account has been restricted due to unusual activity"*
   - `displayTips.en`: *"We detected unusual activity on this account. Submit feedback to appeal this restriction"*
   - `actions: ["EDIT_INPUT", "SUBMIT_FEEDBACK"]`
3. 封号前最后一次成功请求 **10-26 22:58**；23:33 起反代全量失败；**10-27 00:37 官方客户端用同一账号也 403/11140**
   ⇒ 限制作用在**账号**上，与反代实现无关。
4. 主因排序（强→弱）：**多账号 + 极端用量**（强）→ **非官方客户端特征**（中强）→
   **上游 10 月下旬批量收紧**（中强）→ **429 秒切号**（中）→ IP 信誉（弱-中）→ TLS 指纹（不成立）。
5. 本质：**"多账号批量注册 + 非官方客户端 + 极端用量"三者叠加越过账号级阈值**，
   不存在"某一个指纹被命中"这种单点解释，也不存在能靠伪装消除的方案。

## 2. 封禁性质判定

| 判据 | 事实 | 含义 |
|---|---|---|
| 业务码 | `bizCode=11140`, `httpStatus=403` | 账号级风控分支（见下方"双语义"提示） |
| token 是否有效 | `AuthDoInitProbe … hasAccessToken=true`；积分接口仍返回数据 | **凭据未失效**，不是被踢下线 |
| 官方客户端是否可用 | 同账号 + 官方客户端 + 直连 → 同样 403/11140（本地 3 次命中：dagenxuu 两次、lxx0208 一次） | **账号被限制**，与客户端实现无关 |
| 是否额度耗尽 | 是 403 而非 402；文案是"unusual activity"；余额为 0 后仍正常使用过数日 | 不是额度问题（相关但非因果） |
| 是否可申诉 | 响应体带 `SUBMIT_FEEDBACK` + appeal 文案 | 可申诉的风控处置，非永久删除 |

> **⚠️ 复核关键发现——11140 是"双语义"码**（`dingminhua/dsh-connect-workbuddy#127`，2026-10-23 国际站实测；更早的内容审核版见 `linbeize/workbuddy2api-gui#5`，2026-09-17）：
> ① displayMsg「账号存在异常行为，已被限制使用」→ **账号级限制**（换号有效）；
> ② displayMsg「内容未通过安全审核，请调整后重试」→ **请求级内容策略拒绝**（换号无效）。
> 两者 HTTP 403、`code:11140`、`msg:"request illegal"` 完全相同，**只有 displayMsg 能区分**。
> 本案 3 次命中全部是语义①（unusual activity），因此"账号级限制"的判定成立；但反代若要自动化处理 11140，必须按 displayMsg 分流，否则会把内容审核误判成封号（当前代码 `proxy.rs:3861-3888` 未做此区分）。

## 4. 出站指纹清单（代码事实 vs 官方客户端）

官方客户端构造（`<安装目录>/resources/app.asar`，v5.8.4）：
`buildVlmGatewayHeaders(...)` + `applyGatewayHeaders(headers, sessionId, metadata)` + `applyTraceHeaders(...)`。

对照反代 `chat_headers()`（`crates/wb-switch-core/src/modules/proxy.rs:1230-1307`）：

| Header | 官方客户端 | 反代 | 差异 |
|---|---|---|---|
| `User-Agent` | `WorkBuddy/5.8.4 WorkBuddy/5.8.4 CLI/2.161.0` | `WorkBuddy/5.5.4 WorkBuddy/5.5.4 CLI/2.137.1`（`proxy.rs:40-41`） | 版本落后一个 minor 周期 |
| `X-Product` | `SaaS` | `WorkBuddy` | **取值错误** |
| `X-IDE-Type` | `WorkBuddy` | `desktop` | **取值错误** |
| `X-IDE-Name` | `WorkBuddy` | `WorkBuddy` | 一致 |
| `X-IDE-Version` | 应用版本 | **缺失** | 缺字段 |
| `X-Private-Data` | `true` | **缺失** | 缺字段 |
| `X-Agent-Intent` | `craft` | **缺失** | 缺字段 |
| `X-Agent-Purpose` | `conversation` | `conversation` | 一致 |
| `acp-connection-id` | 会话级连接 ID | **缺失** | 缺字段 |
| `X-Conversation-ID` | = sessionId（带连字符 UUID，会话内稳定） | 每请求新生成 32-hex、**高 16 位恒零** | **格式 + 稳定性双不符** |
| `X-Conversation-Request-ID` | `01a1…` 32-hex（ULID 形态） | 与 Conversation-ID 同值 | 形态不符 |
| `X-Conversation-Message-ID` | `01a1…` 32-hex | 另一随机值（高 16 位恒零） | 形态不符 |
| `X-Request-ID` | `01a1…` 32-hex 或 UUID | 与 Message-ID 同值 | 形态不符 |
| `X-Root-Request-ID` | **官方不存在** | 每请求发送 | 多余字段 |
| `traceparent` | `00-{32hex}-{16hex}-01` | **缺失** | 缺字段 |
| `b3` | `{trace}-{span}-1-{parent}` | **缺失** | 缺字段 |
| `X-B3-TraceId` | 32-hex 随机 | 与 Conversation-ID 同值 | 语义不符 |
| `X-B3-ParentSpanId` | 16-hex 随机 | **缺失** | 缺字段 |
| `X-B3-SpanId` | 16-hex 随机 | **恒为 `0000000000000000`** | **确定性指纹** |
| `X-B3-Sampled` | `1` | `1` | 一致 |
| `Accept` | `application/json` | `application/json, text/event-stream` | 不符 |
| `Accept-Encoding` | 显式 `identity` | 不发送（reqwest 未启用压缩特性） | 不符 |
| `Origin` / `Referer` | 转发时被黑名单过滤，不发送 | 发送上游根地址 | 多余字段 |
| `x-requested-with` | `XMLHttpRequest` | `XMLHttpRequest` | 一致 |
| `x-codebuddy-request` | `1` | `1` | 一致 |
| `X-Device-Token` / Qimei36 / `X-Device-Id-List` | 登录/签到链路携带（图灵盾 SDK） | **完全没有** | 缺设备维度 |

**`X-B3-SpanId` 全零的成因**：`hex_id()` = `format!("{:032x}", nanos ^ 0x5eed…5eed)`
（`proxy.rs:1222-1228`）。2026 年纳秒时间戳远小于 2^64，异或后仍小于 2^64，
格式化 32 位 hex 后**高 16 位恒为零**；`X-B3-SpanId` 取 `msg[..16]`（`proxy.rs:1305`），
于是恒为字面量 `0000000000000000`。由同一值派生的 5 个头都带 16 个前导零，
而官方 ID 是 `01a1…` 前缀或 UUID —— 一次格式校验即可区分。

**协议栈**：`reqwest 0.12` + `default-features=false` + `["json","rustls-tls","stream"]`
（`crates/wb-switch-core/Cargo.toml:16`）⇒ **HTTP/1.1 only**（`Cargo.lock` 无 `h2`），
TLS = rustls + ring + webpki-roots；出站 client 全体账号共享（`proxy.rs:5275-5280`）；
头顺序由 `HashMap` 随机迭代决定（`proxy.rs:1231-1232`，发送见 `3708-3711`）；
出站**不设任何代理**，全部账号共用宿主机出口 IP。

**请求体**：强制 `stream:true` + `stream_options.include_usage=true`（`proxy.rs:1943-1960`）；
`tool_choice` 字符串化（`proxy.rs:2011-2044`）；透传官方不发的 `top_k`/`thinking`/
`enable_thinking`/`chat_template_kwargs`（`proxy.rs:131-145, 1983-1997`）；
国际版注入首条 system（`proxy.rs:2046-2077`）；清洗 `gitStatus:`/`# Environment`/
`developer` 角色/`DeepSeek Harness`（`proxy.rs:1317-1577`）；
**Claude Code 的完整 system prompt 与工具 schema 未经处理进入上游**。

**行为层**：无限速/无并发上限/无抖动；429 不等待直接换号，靠模型级冷却把后续请求轮转到别的号
（`proxy.rs:3804-3857`）；401/403 一律 `mark_failed` → 120s 回池（`proxy.rs:44-45, 573-576`）；
**无 `banned/disabled/11140` 识别**，被封的号每 120s 继续打上游；会话粘滞 TTL 仅 10 分钟
（`proxy.rs:2105-2200`）；后台每日全量 refresh、每 30 分钟签到、可选每 5 分钟 × N 号 × 3 次 billing；
同一 token 在聊天链路用 WorkBuddy UA、在刷新/billing 链路用 Chrome/Mac UA + `X-Client-Platform: web`。

## 5. 检测面全景（服务端视角）

| 层 | 信号 | 可见性 | 本案暴露度 |
|---|---|---|---|
| 网络 | 出口 IP / ASN / 地理 | 必然可见 | 高（6 号同 IP） |
| 网络 | 单 IP 多账号聚类 | 需跨源关联 | **高** |
| TLS | JA3/JA4 | 边缘可见 | 中（机制存在，**无证据 WorkBuddy 使用**） |
| HTTP/2 | SETTINGS/伪头 | 边缘可见 | 不适用（反代是 HTTP/1.1） |
| HTTP | 头族差异 | 必然可见 | **高**（§4 十余项） |
| 应用 | system prompt / tools / 字段形状 | 必然可见 | 高（Claude Code 全量透传） |
| 应用 | 设备指纹（图灵盾/Qimei） | 登录链路可见 | 高（完全没有） |
| 行为 | 用量曲线 / QPS / 节律 | 必然可见 | **极高**（单日 900M tokens、2–3 秒一拍） |
| 行为 | 429→换号 | 必然可见 | 高 |
| 跨账号 | 同 IP / 同指纹 / 同用量形态 | 需跨源关联 | **极高** |
| 账号 | 注册渠道/邮箱/邀请/支付 | 需跨源关联 | 中高 |

工程现实：大厂自动风控的性价比排序通常是"账号/支付图谱 > 配额与用量 > 429/重试模式 >
IP/ASN > 客户端一致性 > TLS 指纹"。本案账号图谱与用量两端都极强，**不需要任何高级指纹即可触发 11140**。

## 6. 外部情报对照（2026-10-27）

- **错误码**（社区逆向，非官方文档）：11128 = 渠道校验失败；**11140 = HTTP 403「request illegal」+
  「账号存在异常行为，已被限制使用」**（与本案错误体逐字吻合）；6004 = 429 模型级频控（本案 10-23 转储即是）。
- **上游收紧时间线**：10-15/16 国际版端点上线渠道校验（11128）；10-20 社区公告"官方开始限制非官方客户端请求"；
  10-21 同类项目（4.5k star）停更，理由第一条为"上游已开始禁用反代……识别与拦截正在收紧"；
  10-23 批量 403 增多；**10-26 社区 issue「国际版开始封号了」——"六个号一起封了（可能是按 ip 封），
  包括 wb 国际版客户端内也是无法使用"**，与本案形态一致。
- **官方条款**：账号下任何使用均归责于持有人；禁止转让/供他人使用；禁止机器人/绕过保护措施；
  "超出合理正常标准"可限制或暂停；官方明示会检测规避行为。**反代与多账号轮换在条款下均构成违规。**

## 7. 归因排序（含第二轮复核修正）

| # | 假设 | 证据 | 置信度 |
|---|---|---|---|
| 1 | 多账号 + 极端用量被判"异常使用" | 6 号/1 IP/7 天；单日最高 6,469 请求 / 989M prompt tokens；单账号 30 分钟采样间隔内烧完 320+ 积分；11140 文案即"unusual activity" | **强**（复核维持） |
| 2 | 非官方客户端特征 | 十余项确定差异；上游 10-15/16 起渠道校验已被社区 curl 实测（缺任一会话头即 400/11128，`9router#5005`）；登录链路无设备指纹 | 中强（复核维持并加强） |
| 3 | 上游 10 月下旬批量收紧 | 10-15 渠道门上线；10-21 同类项目停更（原文核实，4,550 stars）；10-23 多起"国际版几个号全被端"（hub#629/#636）；10-25~26 收紧警告与打卡 11140 | **强**（复核升级：外部一手 issue 全部核实） |
| 4 | 429（6004）后秒切号被识别为绕限额 | 10-23 转储为 6004；429 不等待换号 | 中 |
| 5 | 内容违规（替代假设，已专项反证） | 9 月会话含高危主题；但正文已灭失、无法映射到被封账号；**无法解释 6 号同晚批量被封**；封号前一周流量为正常开发内容；官方客户端发无害消息仍 403 | **不成立为主因**（最多是无法排除的次要贡献项） |
| 6 | 出口 IP 信誉/ASN | 6 号同 IP；但同机国内付费号未封；社区 hub#661 显示同账号 chat 200 仅打卡 403，反证"按 IP 封" | 弱（下调） |
| 7 | TLS/JA3 指纹 | 无任何证据；反代为 HTTP/1.1 | 不成立 |

**复核后新增的重要外部事实**：
- 11140 双语义（账号级 vs 请求级内容审核）——`dsh-connect-workbuddy#127`、`workbuddy2api-gui#5`（2026-09-17 即有内容审核版）。
- 封号分布特征三类都有公开案例：**部分账号幸存**（hub#422）、**单账号也被封**（magpie#2152）、**国际版集中爆发而国内版基本没事**（hub#629/#636；但国内版 10-20/21 也出现 11128 与账号级 403，`dsh-our-free-model#559`）。
- 上游检测维度包含**系统提示词指纹**（magpie#3089："refuses chats from Codex and Claude Code (their system prompt)"；`dsh-our-free-model#568`："上游有两个提示词指纹"）——与本地发现的"Claude Code system prompt/tools 全量透传"直接对应。
- 社区曾以 mitmproxy 抓官方 5.8.4 客户端约 350 条流量对齐出站身份（hub PR#381，2026-10-15/16），旁证官方客户端头族确为上游校验对象。
- "按 IP 封"与"官方客户端内也无法使用"的社区转述**未找到原始出处**，且 hub#661 构成反证——已从结论中降权。

**"自用"不构成抗辩**：服务商的合同对象是"一个账号/一个席位"；多账号轮换以突破单账号配额，
在条款与风控模型里就是账号共享/转售/滥用，是否收费不影响定性。

### 复核中的代码层勘误（对第一轮报告的修正）

1. "**不读取/不记录上游 403 响应体**"为错误表述：响应体被读取（`proxy.rs:3747`）并参与分类；存在 `~/.wb-switch/DEBUG_DUMP` 开关文件时会完整落盘 `dump/last-failure.txt`（`proxy.rs:3780-3787`），且未特判错误的响应体会**原样回传给客户端**（`proxy.rs:3902-3907`）。正确说法是"默认不落盘、不解析 11140/unusual activity"。
2. "唯一 sleep"不准确：出站链路有 3 处固定/线性重试退避（400ms/200ms/300ms×n，`proxy.rs:3729/3764/3771`），无随机抖动。
3. `X-B3-TraceId` 同样恒以 16 个零开头（与全零 SpanId 同源的确定性指纹）。
4. 环境变量代理（`HTTP(S)_PROXY` 等）对**所有** reqwest 客户端自动生效；而系统级代理设置（Windows 注册表）因 `system-proxy` 特性关闭反而不生效。
5. 入站带 `X-Conversation-ID` 时出站会带**两个同名头**（`reqwest .header()` 为 append 语义，`proxy.rs:1298+3714`）；代码注释"不吞、不改、不新增"与实际行为不符。

## 9. 对"如何避免被封"的结论

- **无效**：换 UA/补头/改 ID 格式（跨层一致性一验即穿）、加 IP 代理（账号图谱仍在）、
  指纹随机化、429 秒切号（本身就是信号）。这类伪装是军备竞赛，且上游 10 月起已把它作为识别对象。
- **有效**：官方客户端、单账号、人类节奏、不批量注册、不跨账号轮换、用量控制在套餐设计范围内。
- **现实**：本次属可申诉的风控处置，但账号已带"unusual activity"标记；在多账号 + 非官方客户端前提下
  **申诉成功率低**，且条款本身禁止相关用法。继续以多账号反代方式使用，**再次触发是时间问题**。
