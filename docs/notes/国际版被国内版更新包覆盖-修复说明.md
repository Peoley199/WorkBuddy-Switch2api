# 国际版「打不开」的真相与修复说明

> 时间：2026-10-01 23:04 ~ 23:35
> 结论：**与缓存迁移无关**。是国际版自己的自动更新，被塞进了国内版的安装包。

---

## 一、结论先说

| 你以为的 | 实际发生的 |
|---|---|
| 缓存迁移把国际版搞坏了 | 缓存迁移完全正常，联接和 F 盘数据都好好的 |
| 切换账号触发了 bug | 切换账号只是**让它重启了一次**，重启时它把待安装的更新装上了 |
| 国际版文件丢了 | 文件在，但**身份被换成了国内版**（程序目录里的 `product.json` 被覆盖） |

## 三、根因

**`%LOCALAPPDATA%` 下的更新缓存是「按用户」而不是「按产品」隔离的。**

国际版（5.6.2）启动时看到缓存里有个「版本号更高」的安装包就直接套用了，
**没有校验这个包属于哪个产品**。而「切换账号会先关掉应用再重开」正好提供了那个重启时机。

### 1. 重建了一个国际版程序目录

```

取值全部来自**国际版自己缓存在数据目录里的服务端配置**
`C:\Users\<用户名>\.workbuddy-ai\cache\acc-product-config-v3.json`：

| 字段 | 改前（国内） | 改后（海外） |
|---|---|---|
| `productName` | WorkBuddy | WorkBuddy AI |
| `dataFolderName` | .workbuddy | **.workbuddy-ai** |
| `endpoint` | www.workbuddy.cn | www.workbuddy.ai |

> 说明两者是同一套 schema。`commands` 这个只存在于磁盘版里的键被保留了下来。

`WorkBuddy AI.lnk`（桌面 + 开始菜单）原来指向 `<安装目录>\WorkBuddyAI\WorkBuddyAI.exe`

原文件备份为同目录下的 `WorkBuddy AI.lnk.orig.bak`。

### 3. 隔离了那个会误套用的安装包

```
installer.exe  →  installer.exe.quarantine-20261001-231621

（在 `%LOCALAPPDATA%\@genieworkbuddy-desktop-updater\`，526 MB，没删，只是改名）

## 八、给你的两条防护建议

1. **不要指望 `WORKBUDDY_UPDATE_URL=http://127.0.0.1:1` 挡更新。**
   你现在设了这个用户级环境变量，但它**挡不住已经下载到缓存里的安装包** ——
   那条路径根本不看 URL。真正有用的是：别让两个版本的更新缓存混在一起。
2. **以后再遇到「某个版本打不开」，先看 `~/.workbuddy-ai/logs/startup/` 最新那份日志的
   头两行**：里面直接写着 `argv=[...]`（是哪个 exe 起的）和 `CodeCache dir=...`
   （用的是哪个数据目录）。这两条就能立刻判断它是「哪个版本、读哪份数据」。
3. 国际版如果哪天自动更新又出问题，去
   `resources\app.asar.unpacked\cli\product.json` 看 `dataFolderName` 和 `endpoint`
   两个字段，一眼就知道身份对不对。

## 九、第二轮排查（10/2 00:00–00:25）：第一次双击为什么还是没窗口

### 找到第二层原因：启动器 exe 与 resources 不是同一代

安装目录里两个 exe **字节数完全相同（204,585,008）但哈希不同**：

| 文件 | 日期 | SHA-256（前 16 位） | 是什么 |
|---|---|---|---|
| `WorkBuddy.exe` | 09-30 | `b7afeb6bbbe604f4` | 5.7.3 启动器 —— 能正常跑 |
| `WorkBuddyAI.exe` | 09-23 | `73341e9ce8cbea3b` | **5.6.2 启动器** —— 被今晚的安装留了下来 |

今晚 23:00 的安装把 `resources/`（app.asar、`snapshot_blob.bin`、`*.pak`、`icudtl.dat`）
整体换成了 5.7.3，**但没动 `WorkBuddyAI.exe`**。用老启动器配新资源，进程起来就退出。

已处理：用 5.7.3 启动器覆盖 `WB-Overseas\WorkBuddyAI.exe`（哈希核对一致），
老的备份为 `WorkBuddyAI.exe.5.6.2-launcher.bak`。

### 一句话说明「为什么之前的自测结果不算数」

我先前从命令行起的几次都「秒退」，一度以为是应用坏了。后来拿
**已知运行正常的** `<安装目录>\WorkBuddyAI\WorkBuddy.exe` 做对照（还专门给了它一个
独立数据目录，不可能撞锁）—— **在命令行里同样起不来**，那个独立目录连创建都没有。

所以：**命令行能起不来 ≠ 应用坏了**。这个环境的命令行起不了 GUI 应用，验证只能靠你点。

顺带查清了「秒退 + 没有任何日志 + 没有崩溃报告」这条路径：

```js
const gotTheLock = app.requestSingleInstanceLock();
if (!gotTheLock) {
    startupLog("SingletonLock failed: another instance running or userData dir inaccessible");
    app.quit();
    process.exit(0);        // 退出码 0、无窗口、无痕
}
```

即：**单实例锁没拿到**（另一个实例在跑，或数据目录不可访问）。
另外，从这个环境的命令行启动应用时，会继承正在运行的国内版注入的
`WORKBUDDY_CONFIG_DIR=...\.workbuddy`，于是新实例也用国内数据目录 → 必然撞锁。

### 现在请你点一次（两种都行）

1. **先试桌面上的「WorkBuddy AI」图标** —— 启动器已经换成 5.7.3，和上次不是一个配置了。
2. 如果还是没窗口，双击桌面上的 **`WorkBuddyAI-diag.cmd`**
   （桌面上新出现的一个黑窗口脚本，纯英文，跑完会停住等你截图）。
   它会把**退出码**打出来，这个数字直接指向原因：

| 退出码 | 含义 |
|---|---|
| `0` | 单实例锁没拿到（还有实例在跑）／干净退出 |
| `1` | JS 未捕获异常（早期初始化报错） |
| 负数（如 `-1073741819`） | 进程崩溃 |

把那个黑窗口截图发我即可。用完可以直接删掉这个脚本。

## 十、结果：国际版已恢复（10/2 00:26）

换成 5.7.3 启动器后**窗口正常出来了** —— 标题栏 `WorkBuddy AI 5.7.3`，侧栏是国际版界面，
左下角账号还是 `账号-国际-1`，说明读的正是 `~/.workbuddy-ai` 那份数据。身份完全正确。

随后出现的唯一提示是启动自检弹窗：

> **WorkBuddy AI 启动修复** — WorkBuddy AI 安装文件损坏或缺失，无法自动修复，请重新安装 WorkBuddy AI。

### 它为什么报这个

`RepairApp.exe` 会按 `resources\install-manifest.json` 的清单核对安装文件**是否存在**
（它的字符串特征：`missing-binary:`、`*buddy.exe`、`cli/product.json`、`unpacked-dir-missing`；
asar 完整性检查因为没有 manifest 会跳过）。

拿「已知正常的国内版目录」和「国际版目录」做文件清单 diff，**只缺一个文件：`WorkBuddy.exe`** ——
那是我先前做对照实验时当成「多余副本」删掉的。而这个目录里**两个 `*buddy.exe` 都必须在**。

已处理：
- 把 `WorkBuddyAI.exe`（5.7.3）复制一份为 `WorkBuddy.exe`，补齐清单；
- 我在安装目录里加的 `.bak` 备份全部移到 `<安装目录>\WB-Overseas-backups\`。

复查结果：**缺失文件 = 无**；与正常目录的唯一差异只有 `product.json`（正是我们改的身份配置）。

> **重启一次国际版**，自检就不再弹这个框了（它是启动时跑一次的 preflight）。
